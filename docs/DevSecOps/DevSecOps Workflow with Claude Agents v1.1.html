DevSecOps workflow with Claude agents

Proposal v1.1, updated 2026-11-27. Superseded by v3.

Agents propose, gates decide, every cycle teaches

A git-first workflow for Gitea or GitLab on k3s. Claude agents plan, build and review; every thought, decision, task and learning lands in the repo as reviewable text, and a human approves every merge. Pick a stage to see what it needs and which model runs it.

    Foundation principles

    Ten rules every repo, agent and person follows. When in doubt, these win over convenience.

      Where each thing lives

      Work items live in the tracker and get closed. Knowledge lives in the repo as files and gets read by agents.

        Learnings that change behaviour

        A learning only counts when it changes something an agent or pipeline reads. Each item is promoted to the strongest place that can hold it.

        1. 1. CI ruleIf a check can enforce it, write the check. A Semgrep rule banning raw SQL strings.
        2. 2. CLAUDE.mdJudgement, not mechanics. “Don’t add a new service without a health endpoint.”
        3. 3. ADRWhen the learning changes a decision.
        4. 4. Learnings logContext worth keeping that isn’t a rule.

        Obsidian setup rules

        1. Personal vault in its own private git repo, synced with the obsidian-git plugin.
        2. A note that becomes a decision, task or learning moves to the repo, and the note links to it.
        3. One vault per confidentiality boundary: Coremont material never shares a vault with Comurg or personal notes.
        4. A CLAUDE.md at the vault root describes the layout and what is off-limits to agents.

        Gitea or GitLab

        Both work. Gitea is the lighter fit for a 3-node k3s cluster and a small team; GitLab wins if native epics, approval rules and security dashboards matter more than resources.
